# Model Data Conversion

Kadoka Othello AI uses `ModelRecord` as the internal interchange model.
External formats are converted through static field mapping tables.

## Principle

```text
External format
    <->
StaticFormatMapping
    <->
ModelRecord
    <->
StaticFormatMapping
    <->
External format
```

The converter must not contain format-specific AI logic. A new format should normally require only a new `StaticFormatMapping` plus an encoder/decoder for any rule kind that does not already exist.

## Built-in mapping IDs

| Format ID | Name | Import | Export | Notes |
|---|---|---:|---:|---|
| `csv.v1` | CSV | yes | yes | Complex fields are JSON strings inside cells |
| `tsv.v1` | TSV | yes | yes | Same mapping as CSV with tab separator |
| `json.v1` | JSON | yes | yes | One or more structured records |
| `jsonl.v1` | JSON Lines | yes | yes | One record per line |
| `numpy.npz.v1` | NumPy NPZ | yes | yes | Array-oriented training format |
| `pytorch.tensor.v1` | PyTorch Tensor Dataset | yes | yes | Tensor-oriented training format |
| `othello.kifu.text.v1` | Plain Othello Move List | yes | yes | Board is reconstructed from move sequence |

## Static field mapping

Each `FieldMapping` declares:

- Kadoka `ModelRecord` field
- external field name
- logical field type
- conversion rule
- optional rule parameter
- whether the field is required

Supported rule kinds initially include:

- direct copy / rename
- board flattening or string encoding
- position pair or flat-index conversion
- position-list conversion
- JSON embedding for complex fields
- constant/default value
- ignored/non-representable field

## Canonical values

Unless a format-specific mapping overrides them:

```text
Cell:
  Empty = 0
  Black = 1
  White = 2

Position pair:
  row, col

Flat position index:
  row * board_size + col
```

This keeps conversions deterministic and makes static table-driven conversion possible.

## Lossy conversions

Some formats cannot represent every Kadoka field. For example, a plain move-list record cannot directly store candidate evaluations or diagnostics. Those fields use the `Ignore` rule and must be documented as lossy.

When importing a move list, board state and legal moves are regenerated by replaying the moves through the Core engine.

## Extension

Additional common formats can be added without changing `ModelRecord`. Examples planned for later implementation include:

- Parquet / Arrow
- HDF5
- SQLite datasets
- raw binary packed records
- external engine-specific game formats
- custom research datasets

The preferred route is always `external <-> ModelRecord`, rather than maintaining direct converters between every pair of external formats.
